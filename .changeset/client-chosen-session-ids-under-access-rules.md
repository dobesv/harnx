Allow callers with `prompt` scope to create sessions with client-chosen IDs by sending a first prompt when access rules are enabled.

When access rules are enabled on `harnx-serve`, `POST /v1/agents/{agent}/sessions/{session}` no longer requires pre-allocating a session ID via `POST /v1/agents/{agent}/sessions` (which remains available for reserving server-generated short IDs). A caller with `prompt` scope now creates and claims a client-chosen ID on its first qualifying prompt: for JSON-RPC (`Content-Type: application/json`), a `session/prompt` with nonblank `text` or non-empty `attachment_refs` and no `resume` entries (attachment-only prompts still require a `text` field, which may be `""`); for SSE (`Accept: text/event-stream`), a valid AG-UI run input with no `resume` decisions whose last supported message (after dropping unknown roles) is a nonblank `user` message. The session ID must be a safe path segment with no leading or trailing whitespace and satisfy the runtime's `SessionRef` validation (`[A-Za-z0-9_-]+` of at least 6 characters, matching attachment uploads); IDs that fail (such as `demo` or `pr.12`) receive the same opaque guard HTTP `404` without claiming or falling back to a generated ID.

Callers without `prompt` scope (such as `admin`-only callers) receive HTTP `403 Forbidden` (`session creation requires prompt scope`) on a qualifying creating prompt to an unseen ID, with nothing created. Every other request on an unseen ID (non-prompt RPCs, blank or `resume`-bearing prompts, promptless or `resume`-bearing SSE runs, malformed requests, non-`POST` methods, deeper subroutes, existing orphan `SESSION_` streams without metadata, or a live local actor without canonical metadata) returns the same HTTP `404 Not Found` as an inaccessible session for refused (404) outcomes; this parity doesn't cover every partial-outage outcome. For `POST /v1/agents/{agent}/sessions/{session}` with a claimable ID and no deeper segments, both unseen and foreign-owned IDs reject a declared `Content-Length` over 20 MiB immediately with `404` before reading any body bytes, and otherwise share a bounded body read (20 MiB cap, 30-second deadline) returning `404` when over the cap or unfinished at the deadline. Proxies or ingresses in front of `harnx-serve` must allow at least 20 MiB bodies and a 30-second upload time for claim-candidate `POST`s. Pre-reservation attachment checks run before reservation: denials, malformed refs, or `>32` `cid:media` refs return the guard's HTTP `404`, and preflight broker outages return HTTP `503`, leaving the ID unclaimed. Broker outages during metadata reservation on unseen IDs also return HTTP `503` with the guard's JSON error body, not JSON-RPC `-32003` (including post-connect KV write timeouts, broken pipes, or no responders), without admitting the prompt, though a reservation outage after canonical KV creation committed can leave the ID claimed by the caller so a same-caller retry resolves as owned. Concurrent creators race atomically in NATS KV (`SessionMetadataStore::create`), with the winning record authorized against the caller.

Session deletion (`harnx delete session` and worker retention GC) now purges the canonical metadata key `sessions/<owner>/meta` last, after the transcript stream, lease, invocation journal, non-canonical metadata keys, interaction checkpoints, media, plans, and A2A state. A partial deletion keeps the old owner so other prompt-only users cannot claim the ID until deletion is re-run or collected by retention GC (note that retrying deletion rewrites the invocation journal's 1-hour tombstone, which refuses journaled tool calls on the reused ID for another hour without blocking the claim itself). If the canonical record's revision changed during deletion, the final purge is skipped instead of removing the newer record: the CLI prints `Incomplete deletion of remote session` (including `metadata_keys_deleted`) to stderr and exits `1`, and retention GC counts `skipped_metadata_changed` instead of `deleted`. Once fully deleted, anyone with `prompt` scope can reuse the ID.

**Upgrade order and operator notes:** On clusters that use access rules, upgrade every component that deletes sessions (`harnx` CLI, and `harnx-worker` instances running retention or orphan GC) and let any in-flight old cleanup runs finish **before** upgrading `harnx-serve` (there is no feature flag). Older deleters purge canonical metadata before media and plans and would leave claimable partial deletions. When rolling back, roll back `harnx-serve` **before** rolling back the deleters. Finish retrying `harnx delete session` on any sessions whose deletion failed before canonical-last ordering before enabling or upgrading to a `harnx-serve` with client-chosen claims, so leftover media or plans cannot be reached by a later claimant or deleted on a late retry.

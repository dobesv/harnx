Define custom agent-facing script tools backed by in-process BashKit Bash or Monty Python scripts that can call other allowlisted tools. Script tools can be defined globally in `config.yaml` (`script_tools:`) and in packages (`packages/<pkg>/script_tools/*.yaml`, one definition per file). Each definition specifies a name, description, JSON Schema `parameters` (with required top-level `type: object`), an opt-in `tools:` allowlist, an inline `bash` or `python` script body, an optional timeout (default 300s), and an output mode (`text` or `json`). Validated arguments are available via the `tool_input` command (Bash) or `tool_input()` function (Python). In Bash, allowlisted tools run as commands with standard CLI flags and exit codes; in Python, scripts call `call_tool(name, args)`. Script tools are exposed to models through standard `use_tools` selectors (literal names, globs, toolsets) and can be called from `bash` script mode via `bash_tools`. Inner calls pass through agent middleware, cannot prompt for interactive approval, and cannot call `bash`, control tools, or other script tools. Base-tool name collisions keep the original tool and disable the script tool with a warning. Locally managed workers start tool servers required by selected script tools automatically. Definitions are read at startup: adding or changing them takes effect after a config reload or restart. Older binaries ignore the `script_tools:` key and package `script_tools/` directories, so a downgrade leaves definitions unread and the tools simply absent rather than erroring. When package directories resolve to the same canonical path (for example, through symlink aliases), Harnx loads tool servers, clients, and script tools only from the first name in sorted order and skips aliases with a warning.

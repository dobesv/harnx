Web UI attachment upload failures now return a fixed, credential-free error message instead of echoing the internal failure chain (which included the NATS object-store key). The full chain stays in the server log, with credentials in common NATS URL forms (URL userinfo like `nats://user:pass@host`, and query-string tokens on both schemed and schemeless `host:port?token=...` addresses) masked before upload errors are logged. Upload-path failures that reach the upload error mapper with a recognized broker-unavailability cause return 503 "attachment object store is unavailable"; other store failures return 500 with the fixed, credential-free generic message. Unavailability is classified by typed error causes rather than message text — the JetStream API wrapper errors (no responders, cluster not available, stream offline, exhausted retry budget), a failed bucket ensure on a lost connection, a connection-state fallback for puts whose publish errors were stringified, and a failed dedup-probe read whose typed cause chains into a put that then lost its own. With access rules enabled, the same classification maps an unreachable metadata broker in the upload ownership guard to a 503 instead of the generic 400; the guard answer keeps the request-error envelope, so its message text varies with the failure, unlike the upload error mapper's fixed 503 body. A put whose old-chunk cleanup fails after the new version committed no longer fails the upload: the committed version is reported and rechecked like any other, but only when the re-read metadata is provably this put's own version, so a concurrent replacement or a deleted record fails the upload without purging anyone else's object, and the un-purged previous chunks become invisible orphans. Not covered: a put against a warm bucket whose JetStream stops answering mid-write without leaving a typed cause still returns 500.

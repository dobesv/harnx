Web UI attachment uploads no longer leave behind the version a part wrote when the session turns out to be deleted or replaced while the upload is in flight. The upload captures the session's incarnation (`created_at`) from its metadata before the first stored part and rechecks it after every acknowledged object-store put, before the ref is returned. If the session is confirmed gone, or was recreated under the same id with a new incarnation, the upload answers 404 with no refs and removes only the object version the failed put itself wrote — never the whole owner/name, and a dedup hit purges nothing. Object versions committed for earlier parts of the same request remain (they are content-addressed and harmless). Known residual race, as documented on `purge_version_of_gone_session`: a concurrent upload of the same content can dedup-hit the just-written version between its commit and this purge, and the ref that upload returned can then point to removed data. A recheck that fails on transport keeps the F3 failure contract: 503/500 per the connection-state classification, and nothing is purged. Sessions that were never created (no metadata record) upload as before. With access rules enabled, the guard proves the session exists before the upload body is read; when the session's record is absent by the time the upload stores its first part (it was deleted between the guard and the store), the upload answers the same 404 instead of storing unrechecked, and rules-on uploads to an already-deleted session answer 404 before reading or storing anything.
